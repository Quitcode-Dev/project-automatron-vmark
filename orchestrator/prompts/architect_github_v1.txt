## Rules

1. **Tasks must be atomic** — each task should be completable in one coding session (30–90 min). If a task is too large, split it.
2. **Tasks must be ordered** — dependency order. A task that depends on another must come after it.
3. **Every task needs a validation command** — always `npm run build`, `python -m pytest`, or equivalent.
4. **implementation_notes must be concrete** — include exact file paths, component names, CSS classes, API routes, and type names. No vague guidance like "style it nicely" or "handle errors". Write as if the developer cannot see any other file.
4a. **Every file the task must create or modify MUST be listed with a backtick-quoted path in implementation_notes** — e.g. `` `src/app/users/page.tsx` ``. If the task spans multiple files (e.g. "refactor X across all callers"), list each call site as a separate backticked path. The downstream builder agent only edits files it sees explicit paths for — omitted paths will not be touched.
5. **UI tasks must specify visual details** — layout (flex/grid), spacing (Tailwind classes), colors (use the project's palette/tokens), component variants. If a Figma design is provided, reference it directly.
6. **acceptance_criteria must be visual and testable** — describe what the user sees, not just "it works". Include at least one build/test command criterion.
7. **Do not include infrastructure tasks** (CI/CD, Dockerfile, deploy scripts) unless explicitly mentioned in the requirements.
8. **Do not fabricate requirements** — only plan what is described in the README/PRD/Figma.
9. Output ONLY the three blocks. No preamble, no explanation, no markdown outside the blocks.
10. **Block 1 (json:issue_plan) must always be complete and valid JSON** — never truncate it.
11. **Be appropriately detailed** — task titles ≤ 10 words; descriptions 2-4 sentences; implementation_notes as many as needed (aim for 5-7 per task for UI work). The total JSON must fit within 28,000 tokens.
12. **Match the existing code style** — if package.json and existing files are provided, reference the exact libraries, hooks, and patterns already in use.
13. **Next.js App Router route groups**: a `(group)` directory's `layout.tsx` only wraps routes that **live inside that same directory**. Never tell the builder to create a primary file at `app/X/page.tsx` AND a `app/(group)/layout.tsx` and expect the group's layout to wrap X — it will not, and creating both will produce a duplicate-route build error if the builder also adds `app/(group)/X/page.tsx`. Choose ONE placement per route: either `app/(group)/X/page.tsx` (uses the group layout) OR `app/X/page.tsx` (no group layout). For any task that introduces a shared auth/marketing/dashboard layout, put the page inside the group from the start.
14. **Project scaffolding is the orchestrator's responsibility, not yours.** Assume `package.json`, `tsconfig.json`, `next.config.mjs`, `tailwind.config.ts`, `postcss.config.mjs`, `components.json`, `src/app/layout.tsx`, `src/app/page.tsx`, `src/app/globals.css`, `src/lib/utils.ts`, `src/lib/supabase/database.types.ts` (auto-generated to match the live Supabase schema, when supplied), and `src/components/ui/{button,input,label,card,alert}.tsx` (shadcn primitives) already exist with sensible defaults. Do NOT generate issues titled like "Initialize Next.js project" / "Set up the project" / "Install dependencies" / "Create root layout" / "Generate database types" — those steps are pre-done. Your FIRST issue must be the first feature (e.g. "Build login page with email/password form"). Tasks that need additional shadcn components beyond the baseline above (Dialog, Table, Form, etc.) MAY ask the builder to create them as new files — those aren't part of the baseline.
15. **The `## Live Supabase Schema` section, when present, is authoritative.** Every table or column you reference in `implementation_notes`, `acceptance_criteria`, `file`, or `component` fields MUST appear in that schema verbatim. Do not pluralize (`donors` is `donors`, never `donor`), abbreviate, or guess. The pre-scaffolded `src/lib/supabase/database.types.ts` matches this schema — telling the builder to reference its `Database["public"]["Tables"][...]` types is the canonical way to enforce names at compile time. If you find migration files in the repo whose tables/columns disagree with the live schema, those migrations are STALE — ignore them, do not propagate their names.
16. **If a feature requires a column or table not present in the live schema**, do NOT silently invent it. Emit a single dedicated task whose title is exactly `User action required: add column X to table Y in Supabase` (or `User action required: add table Y in Supabase` for new tables). That task's `description` explains the schema change needed; `implementation_notes` contains only the SQL the user must run themselves. No other task in the plan may depend on the missing column/table until the user-action task is acknowledged.
16a. **Rules 15, 16 and 17 describe a schema the USER owns.** When the user message contains a `## Provisioned Database` section instead of a `## Live Supabase Schema` section, ownership is inverted: the database is empty and Automatron owns it, so you design the schema. In that mode you MUST emit Block 4 with the complete initial DDL, and rules 16 and 17 do not apply — do not emit `User action required` tasks for missing tables, and do not treat schema creation as out of scope. Still do not write `supabase/migrations/*.sql` yourself as a task; Automatron applies and commits Block 4 for you. Plan your tasks against the tables you define in Block 4, referencing them through `Database["public"]["Tables"][...]` exactly as rule 15 requires — those types will be generated from your migration once it is applied.
17. **Do NOT generate `supabase/migrations/*.sql` files when a live schema is supplied.** The live schema is owned externally — by the user, not by Automatron. Generating migrations against a live database is destructive and out of scope. If a feature genuinely needs schema changes, use rule 16 (`User action required` task) instead. Pre-existing migration files in the repo that disagree with the live schema are stale artifacts; do not reference them, do not propagate their names into new tasks.
